# 需求拆分

輸入是 `requirement-elicitation` 產出、且使用者已確認的需求摘要。輸出是一份拆單計畫，經使用者確認後交給 `jira-ticket` 建立。

## 拆分規則

### 主單：一個專案、一個可獨立上版的功能，一張主單

- 涉及多個專案時，**每個專案各開一張主單**，因為每張主單對應一個分支，分支只能屬於一個 repo
- 同一個專案內，如果包含多個可以獨立上線的功能，拆成多張主單
- 判斷方法：「這部分單獨上版，使用者能得到完整可用的東西嗎？」可以就拆開

### Subtask：主單內的工作項目

- Subtask 只用來追蹤工作項目，分支、狀態、Test Case 都以**主單**為單位
- 依功能面向拆，例如「折扣計算邏輯」「結帳頁顯示折扣」，不要依技術層拆（例如不要拆成「前端」「後端」「資料表」）
- 每張主單的 subtask 以 2 到 6 個為宜

### 驗收條件的分配

- 每條驗收條件（AC）必須分配到**剛好一張**主單
- 跨專案的 AC（例如「A 系統送出後 B 系統要顯示」）放在下游那張單，並在上游那張單加一條對應的介面 AC

### 相依關係

- 一張單需要另一張單先上版才能運作時，記為「被 ... 阻擋（is blocked by）」
- 標示建議的上版順序
- 避免循環相依；如果出現，代表拆法有問題，重新規劃

## 拆單計畫格式

```
## 拆單計畫

### 主單 1：[SHOP] <標題>
- 驗收條件：AC-1、AC-2、AC-4
- Subtask：
  1. <名稱>
  2. <名稱>
- 相依：無

### 主單 2：[CRM] <標題>
- 驗收條件：AC-3、AC-5
- Subtask：
  1. <名稱>
- 相依：被主單 1 阻擋（需要 SHOP 的新 API 先上版）

### 上版順序
主單 1 → 主單 2
```

產出後問使用者：「這樣拆可以嗎？確認後我會先查重，再建立 Jira 單。」

使用者確認後，交給 `jira-ticket` skill。

## 只有一張單時

需求只影響一個專案、而且不需要再拆時，計畫就只有一張主單，不需要硬拆，直接簡短說明並請使用者確認。
