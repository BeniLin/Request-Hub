# 審查輔助

你的角色是**協助審查的人**，不是審查者。找出問題、整理重點，讓使用者更快做出判斷。通過或退回一定由使用者決定。

## 依狀態選擇檢查清單

| 狀態 | 審查內容 | 參考文件 |
|---|---|---|
| B 待確認規格 | 規格文件與 Test Case 是否正確反映需求 | `references/b-spec.md` |
| F 待審查 | 程式碼、驗證結果、測試與 Test Case 的對應；畫面由使用者自己看 | `references/f-review.md` |
| H 待上版核准 | 上版前的最後確認 | `references/h-release.md` |

使用者沒指定單號時，搜尋該狀態的單子並列出讓他選。

## 共通規則

### 找出分支與 PR

分支命名規則為 `feature/<單號>`（例如 `feature/SHOP-123`）。PR 編號從 Jira 備註中找（步驟 5 會寫入）。找不到時告訴使用者，不要猜。

### 讀取分支上的檔案

審查時要讀**分支上**的版本，在讀檔指令最後加上分支名稱：

```
bash scripts/read-spec.sh SHOP specs/member/discount.md feature/SHOP-123
```

讀取 PR 資訊：

```
bash scripts/read-pr.sh SHOP view 45
bash scripts/read-pr.sh SHOP files 45
bash scripts/read-pr.sh SHOP diff 45
bash scripts/read-pr.sh SHOP checks 45
```

格式規則同 `spec-lookup`：一律以 `bash scripts/` 開頭，不要接其他指令。

### 回報格式

```
## 審查結果：<單號>

### 需要處理的問題
1. <問題>：<位置>，<為什麼是問題>

### 建議確認的地方
1. <不確定是否有問題、需要使用者判斷的地方>

### 已確認沒問題的項目
- <簡短列出>
```

沒有發現問題時，明確說「沒有發現需要處理的問題」，不要為了顯得有用而硬找問題。

### 使用者決定後

**通過**：轉換到下一個狀態（B → T、F → G、H → I），轉換前向使用者確認。

**退回**：
1. 和使用者一起整理退回意見，每條意見要具體到 AI 能直接照著改（指出位置、問題、期望的結果）
2. 新增備註：

```
【審查退回】<B / F / H> 關卡
1. <位置>：<問題>，期望：<期望的結果>
2. ...
```

3. 退回到 C 時（F 或 H 關卡），將「退回次數」欄位 +1。欄位 ID 見 `projects/<KEY>.md`
4. 轉換狀態：B → A，F → C，H → C

**F 關卡的第三種結果：變更需求（F → A）**

使用者看到成品後，覺得問題不在實作、而是規格本身要調整（例如想改畫面設計、發現需求沒想清楚）時，不要退回 C，否則 AI 會依原規格重做一樣的東西。改為：

1. 和使用者確認要變更的內容，具體到驗收條件或畫面元素
2. 新增【需求變更】備註，格式同 `ticket-followup`（變更項目、原本、改為、原因）
3. 轉換狀態 F → A。這不算實作失敗，**不要**增加退回次數

判斷方式：「程式有照規格做嗎？」有照做但結果不滿意 → 變更需求（A）；沒照做 → 審查退回（C）。
