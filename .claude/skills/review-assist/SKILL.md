# 審查輔助

你的角色是**協助審查的人**，不是審查者。找出問題、整理重點，讓使用者更快做出判斷。通過或退回一定由使用者決定。

## 依狀態選擇檢查清單

| 狀態 | 審查內容 | 參考文件 |
|---|---|---|
| B 待確認規格 | 規格文件與 Test Case 是否正確反映需求 | `references/b-spec.md` |
| F 待審查 | 程式碼、驗證結果、測試與 Test Case 的對應；畫面由使用者自己看 | `references/f-review.md` |
| H 待上版核准 | 上版前的最後確認 | `references/h-release.md` |

使用者沒指定單號時，搜尋該狀態的單子並列出讓他選。JQL 中的狀態名稱使用 `CLAUDE.md` 狀態表的完整名稱，例如 `status = "B 待確認規格"`。

## 共通規則

### 找出分支與 PR

分支命名規則為 `feature/<單號>`（例如 `feature/SHOP-123`）。PR 編號從 Jira 備註中找（步驟 5 會寫入）。找不到時告訴使用者，不要猜。

### 讀取分支上的檔案

審查時要讀**分支上**的版本，在讀檔指令最後加上分支名稱：

```
bash scripts/read-spec.sh SHOP specs/member/discount.md feature/SHOP-123
```

讀取 PR 資訊：

```
bash scripts/read-pr.sh SHOP view 45
bash scripts/read-pr.sh SHOP files 45
bash scripts/read-pr.sh SHOP diff 45
bash scripts/read-pr.sh SHOP checks 45
```

格式規則同 `spec-lookup`：一律以 `bash scripts/` 開頭，不要接其他指令。

### 回報格式

```
## 審查結果：<單號>

### 需要處理的問題
1. <問題>：<位置>，<為什麼是問題>

### 建議確認的地方
1. <不確定是否有問題、需要使用者判斷的地方>

### 已確認沒問題的項目
- <簡短列出>
```

沒有發現問題時，明確說「沒有發現需要處理的問題」，不要為了顯得有用而硬找問題。

### B 關卡：「已採用的假設」與「待確認事項」

步驟 3 的 AI 遇到需求沒有寫到的地方，會分成兩類寫進規格文件，並在 Jira 留言中列出：

| 段落 | 內容 | 能不能通過 |
|---|---|---|
| 已採用的假設 | AI 自己決定的細節，已經寫進規則與 Test Case | **不擋通過**。使用者沒意見就可以直接通過，段落保留在文件中 |
| 待確認事項（通常編號 Q-1、Q-2…） | AI 沒有自行決定的關鍵問題 | **不是空的就不能通過**，即使使用者同意目前的寫法。原因是答案只存在於對話或留言中，規格文件還沒有更新，下一步的 AI 會依照未定案的規格寫測試 |

目標是**最多退回一次**。處理方式：

1. **第一次進到 B 就做完整審查**（`references/b-spec.md` 的全部檢查項目，有附件就對照附件），不要等待確認事項清空才審。只回答問題、下一輪才發現規格本身的問題，會多退一次
2. 在**同一則回覆**裡列完三樣東西：
   - 需要使用者決定的：待確認事項，以及你認為其實會改變資料來源、功能範圍或權限的假設。每題說明在問什麼、規格目前怎麼寫，附上具體選項，建議的選項放第一個並標「建議」
   - 審查發現的問題
   - 其餘「已採用的假設」，簡短列出，註明「沒意見就照這樣」
3. 不需要退回時（待確認事項是空的、沒有審查問題、使用者對假設沒意見）：直接依「通過」處理
4. 需要退回時：**在同一則回覆直接附上擬好的【審查退回】備註**，預設採用你的建議，讓使用者回一句（例如「OK」或「第 2 條改成…」）就能完成。備註內容：
   - 每一題的答案寫出**具體內容**，不要寫「照建議」，因為下一步的 AI 看不到這段對話
   - 審查意見與要修改的假設，每條具體到 AI 能直接照著改
   - 引用附件時，把固定文字、版面位置逐字寫出來，不要用簡寫。步驟 3 的 AI 讀不到附件
   - 最後加上「這次修改時遇到需求沒有寫到的細節，直接採用最合理的做法並列入已採用的假設，不要新增待確認事項。以上都處理完後，請清空待確認事項段落」
5. 規格再次回到 B 時：逐條確認上次備註都已處理、待確認事項已清空，再看這次變動的部分與新增的假設。沒有問題就通過，不要重新找上一輪沒提過的小問題來退回；只有會讓實作做錯的問題才再退

### 使用者決定後

每個動作只向使用者確認**一次**：把備註草稿和要轉換的狀態放在同一則回覆，使用者同意後就新增備註並轉換，不要寫完備註再問一次。

**通過**：轉換到下一個狀態（B → T、F → G、H → I），轉換前向使用者確認。

**退回**：
1. 擬好退回意見給使用者看，每條意見要具體到 AI 能直接照著改（指出位置、問題、期望的結果）
2. 使用者同意後新增備註：

```
【審查退回】<B / F / H> 關卡
1. <位置>：<問題>，期望：<期望的結果>
2. ...
```

3. 退回到 C 時（F 或 H 關卡），將「退回次數」欄位 +1。欄位 ID 見 `projects/<KEY>.md`
4. 轉換狀態：B → A，F → C，H → C

**F 關卡的第三種結果：變更需求（F → A）**

使用者看到成品後，覺得問題不在實作、而是規格本身要調整（例如想改畫面設計、發現需求沒想清楚）時，不要退回 C，否則 AI 會依原規格重做一樣的東西。改為：

1. 和使用者確認要變更的內容，具體到驗收條件或畫面元素
2. 新增【需求變更】備註，格式同 `ticket-followup`（變更項目、原本、改為、原因）
3. 轉換狀態 F → A。這不算實作失敗，**不要**增加退回次數

判斷方式：「程式有照規格做嗎？」有照做但結果不滿意 → 變更需求（A）；沒照做 → 審查退回（C）。
