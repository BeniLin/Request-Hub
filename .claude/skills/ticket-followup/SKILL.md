# 單子後續處理

## 列出待處理的單

使用者沒有指定單號時，搜尋狀態為「待人工處理」的單子：

```
project in (<專案KEY>) AND status = "待人工處理" ORDER BY priority DESC, updated ASC
```

列出單號、標題、退回次數、最後更新時間，請使用者選一張。

## 處理一張單

### 1. 了解狀況

讀取單子的描述與**所有備註**，找出 AI 最後提出的問題或卡住的原因。用兩三句話向使用者說明：

- AI 在做什麼的時候卡住
- 它具體問了什麼，或遇到什麼錯誤
- 退回次數（若已達 3 次以上，提醒使用者這張單已多次失敗，可能需要重新檢視需求本身）

需要時用 `spec-lookup` 讀取相關規格，幫助使用者判斷。

### 2. 與使用者討論出答案

跟需求訪談一樣，一次只問一到兩個問題，不替使用者決定業務規則。

### 3. 判斷要壓回哪個狀態

依序問自己兩個問題：

1. **需求、驗收條件或 Test Case 的預期結果需要修改嗎？** 需要 → 壓回 A
2. 不需要的話，**測試腳本需要修改嗎？** 需要 → 壓回 T；不需要 → 壓回 C

| 情況 | 壓回 | 範例 |
|---|---|---|
| 只是實作層面的釐清，Test Case 與測試腳本都成立 | C（待實作） | 「錯誤訊息放在欄位下方」「沿用現有的日期格式」 |
| Test Case 沒錯，但測試腳本的操作方式對不上 | T（待寫測試） | 「這個欄位應該是下拉選單不是輸入框」「需要先登入才能進入頁面」 |
| 需求、驗收條件或 Test Case 需要修改 | A（待撰寫規格） | 「折扣改成 85 折」「新增一種例外情況」 |
| 判斷不出來 | A | 保守處理，讓規格重新被確認 |

注意：如果 AI 回報「測試腳本有誤」，要先確認是腳本真的寫錯，還是實作沒有照規格做。斷言的預期結果與 Test Case 一致時，問題通常在實作，應壓回 C 並說明測試是正確的。

把判斷結果和理由告訴使用者，請他確認。

### 4. 寫入 Jira

**不要修改原本的描述。** 新增一則備註，格式如下：

```
【人工回覆】
問題：<AI 原本的問題，一句話>
回覆：<結論>
處理方式：壓回 <A、T 或 C>，原因：<一句話>
```

如果是需求變更（壓回 A），改用這個格式，讓步驟 3 的 AI 清楚知道要改什麼：

```
【需求變更】
變更項目：<例如 AC-2>
原本：<原本的內容>
改為：<新的內容>
原因：<為什麼要改>
```

壓回 T 時使用這個格式，讓步驟 5 的 AI 知道要修正哪個測試：

```
【修正測試】
測試：<Test Case 編號>
問題：<腳本哪裡對不上>
應改為：<正確的操作方式>
注意：預期結果不變
```

寫入備註後，向使用者確認，再轉換狀態。

## 補充需求（非 D 狀態的單）

使用者想補充一張還沒完成的單子時：

- 狀態 A：直接新增【需求變更】備註即可，不用轉換狀態
- 狀態 B：新增備註後，依 `review-assist` 的規格退回流程壓回 A
- 其他狀態（T、C、E、F、G、H、I）：自動化正在處理中，不要直接轉換狀態。新增備註，並建議使用者等單子到下一個人工關卡（F 或 H）時退回，或請 Jira 管理員手動處理
- 已發版（J）：建議開新單，不要修改已完成的單
