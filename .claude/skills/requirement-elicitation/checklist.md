# 需求檢查清單

每一項都要確認到「完成標準」，才算完整。

## 1. 背景與目的

**完成標準**：能說明為什麼要做、解決誰的什麼問題、做完怎麼知道有效。

參考問題：
- 這個需求是因為什麼狀況而提出的？
- 沒有這個功能的話，目前使用者是怎麼處理的？

## 2. 使用者角色與情境

**完成標準**：列出所有會用到的角色，以及每個角色在什麼情況下使用。

參考問題：
- 誰會使用這個功能？不同角色看到的東西一樣嗎？
- 有沒有角色是**不應該**能使用的？

## 3. 功能描述

**完成標準**：主要流程一步一步寫得出來，沒有「系統自動處理」這種黑箱描述。

參考問題：
- 從使用者進入到完成，每一步會發生什麼事？
- 資料從哪裡來、存到哪裡？

## 4. 驗收條件

**完成標準**：每條都用 Given / When / Then 格式，而且結果可以被客觀驗證（有具體數字、狀態或畫面）。

這是後續 Test Case 的直接來源，品質最重要。

不合格的寫法：「折扣要正確計算」
合格的寫法：「Given 金卡會員購買 1,000 元商品 When 結帳 Then 應付金額顯示 900 元」

參考問題：
- 怎麼判斷這個功能做對了？請給我一個具體例子。
- 邊界值是多少？（例如剛好 1,000 元算不算？）

## 5. 例外與錯誤處理

**完成標準**：常見的例外情況都有明確的處理方式與使用者看到的訊息。

逐一確認：
- 輸入格式錯誤或空白
- 權限不足
- 資料不存在或已被刪除
- 外部服務失敗或逾時
- 重複操作（例如連點兩次）

## 6. 畫面需求

**完成標準**：有設計稿，或有足夠具體的文字描述（位置、元件、文字內容）。

參考問題：
- 有設計稿或參考畫面嗎？
- 沒有的話，這個功能出現在哪個頁面的哪個位置？

如果完全沒有畫面變動，明確記錄「無畫面變動」。

## 7. 不做的範圍

**完成標準**：至少列出一項明確排除的內容，或確認真的沒有需要排除的。

這一項可以防止後續實作時自行擴充範圍。

參考問題：
- 有沒有相關但這次不做的部分？
- 既有的資料需要一起處理嗎？還是只影響新資料？

## 8. 影響範圍

**完成標準**：列出會受影響的現有功能、規格文件，以及其他專案。

參考問題：
- 這個改動會影響哪些現有功能？
- 其他專案有用到這裡的資料或介面嗎？
