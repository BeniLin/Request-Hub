# 需求訪談

目標是把使用者腦中的想法，變成一份**後續 AI 不需要再猜**的需求。步驟 3 的 AI 會依照這份需求寫規格和 Test Case，任何模糊的地方都會變成錯誤的實作，所以寧可多問一題，也不要自己補。

## 流程

### 1. 確認專案

讀取 `projects/registry.csv`。如果使用者沒說是哪個專案，且從描述中無法明確判斷，列出專案請他選。可能涉及多個專案時，先記下來，到第 5 步交給 `requirement-split` 處理。

確定後讀取 `projects/<KEY>.md`，了解這個專案的領域名詞與注意事項。

### 2. 先讀現有規格，再開始問

使用 `spec-lookup` skill 讀取該專案的 `INDEX.md`，找出跟這個需求相關的規格文件並讀過。

這一步很重要：讀過現有規格，才能問出「現在的規則是 X，新需求是要取代還是並存？」這種有根據的問題，也才能發現衝突。

### 3. 依清單逐項問答

依照 `checklist.md` 的八個項目逐一確認。規則：

- **一次只問一到兩個問題**，並說明為什麼要問（一句話即可）
- 能從現有規格得知的，不要問使用者，直接說明「依照現有規格 `specs/xxx.md`，目前是 ...，這次維持不變對嗎？」
- 使用者的回答模糊時（例如「大概」「看情況」「跟之前一樣」），追問到具體
- 需要提供選項時，列出 2 到 3 個具體做法讓使用者選，並說明各自的影響
- 使用者提供截圖或設計稿時，描述你看到的重點，確認理解正確

每問完 3 到 4 輪，簡短回報進度，例如：「目前已確認：背景、角色、功能流程。接下來確認驗收條件。」

### 4. 處理假設與衝突

- 你需要自行推定的任何事，都明確寫成「**假設：...，請確認**」，不要直接寫進需求
- 發現與現有規格衝突時，立刻指出：「這跟 `specs/xxx.md` 第 N 節的規則衝突：...，要以哪個為準？」

### 5. 產出需求摘要並確認

八個項目都確認、而且沒有未回答的假設後，依照下方格式產出摘要，並問使用者：「以上內容正確嗎？確認後我會規劃拆單。」

使用者確認後，交給 `requirement-split` skill 規劃拆單，再交給 `jira-ticket` skill 建單。

**不可以在使用者確認前建單。**

## 需求摘要格式

```
## 需求摘要：<一句話標題>

**專案**：<KEY>（若涉及多個專案全部列出）

### 背景與目的
### 使用者角色與情境
### 功能描述
### 驗收條件
- AC-1：Given ... When ... Then ...
- AC-2：...
### 例外與錯誤處理
### 畫面需求
### 不做的範圍
### 影響範圍
### 相關規格文件
- `specs/xxx.md`：<關係說明，例如「需修改第 3 節的折扣規則」>
### 決策紀錄
- <討論中做過的重要決定，以及被否決的選項和原因>
```

「決策紀錄」很重要：其他人看不到這段對話，這是他們理解「為什麼這樣做」的唯一依據。

## 需求太大時

如果驗收條件超過 10 條，或包含多個可以獨立上線的功能，建議使用者拆成多個需求分別討論。一張單應該是可以獨立開發、獨立驗證、獨立上版的單位。

## 不要做的事

- 不要撰寫規格文件、Test Case 或程式碼，那是後續自動化步驟的工作
- 不要替使用者決定業務規則
- 不要為了加快速度一次問很多題
