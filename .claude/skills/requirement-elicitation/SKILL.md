# 需求訪談

目標是把使用者腦中的想法，變成一份**後續 AI 不需要再猜**的需求。步驟 3 的 AI 會依照這份需求寫規格和 Test Case，任何模糊的地方都會變成錯誤的實作。

但使用者的耐心有限。一題一題問細節，會讓簡單的需求拖成冗長的訪談。所以做法是：**只問真正需要使用者決定的事，細節由你提出預設值，寫進摘要草稿讓使用者一次確認。** 模糊的地方不是靠多問來消除，而是靠「把預設值明確寫出來」來消除。

## 流程

### 1. 確認專案

讀取 `projects/registry.csv`。如果使用者沒說是哪個專案，且從描述中無法明確判斷，列出專案請他選。可能涉及多個專案時，先記下來，到第 6 步交給 `requirement-split` 處理。

確定後讀取 `projects/<KEY>.md`，了解這個專案的領域名詞與注意事項。

### 2. 先讀資料與現有規格，再開始問

- 使用者提供的檔案（截圖、PDF、範例）先看完
- 使用 `spec-lookup` skill 讀取該專案的 `INDEX.md`，找出跟這個需求相關的規格文件並讀過

能從規格或資料得知的事，一律不問。

### 3. 第一次回覆：理解＋分類＋關鍵問題

第一次回覆依序包含：

1. **你的理解**：資料裡有什麼、現有系統已經有什麼、缺什麼，簡短列出
2. **與現有規格的關係**：哪些已經被現有規則滿足、哪些衝突（註明文件與章節）
3. **預告**：「接下來大約還有 N 輪問題，其餘細節我會整理成假設清單讓你一次確認」
4. **關鍵問題**：最多 2 到 3 題，編號列出

把每個待定事項分成兩類：

| 類別 | 判斷方式 | 處理 |
|---|---|---|
| **關鍵決策** | 答案會改變功能的架構或資料來源（放在哪個流程、資料從哪裡來、要不要新畫面），而且沒有合理的預設 | 問使用者 |
| **細節** | 有合理、常見的做法（顯示格式、留空或失敗、權限沿用、檔名、上限、錯誤訊息、邊界值） | 不問，直接定預設值，標 ⚠️ 寫進摘要草稿 |

拿不準屬於哪一類時，歸為細節，用 ⚠️ 讓使用者在草稿裡改。

### 4. 問答輪數上限

- 每輪最多 2 到 3 題，需要選擇時列出 2 到 3 個具體選項並說明影響，**把你建議的選項放第一個並標「建議」**
- 使用者的回答模糊時，追問一次；還是模糊就定預設值標 ⚠️
- **關鍵問題最多 3 輪**。3 輪後即使還有不確定的地方，也直接進入第 5 步，把剩下的都寫成 ⚠️
- 使用者表現出不耐煩（例如問「還有幾題」「怎麼這麼多」），**立刻停止發問**，直接進入第 5 步

`checklist.md` 是你自己檢查摘要是否完整的清單，**不是要逐項問使用者的問題清單**。每一項只要有使用者的答案、現有規格的依據或標 ⚠️ 的預設值，就算完成。

### 5. 產出摘要草稿（含 ⚠️ 預設值）

依照下方格式產出完整摘要。凡是你自己定的內容，在該行前面標 **⚠️**，不要混在已確認的內容裡不標。

草稿前面用一句話說明：「標 ⚠️ 的是我定的預設值，有不對的直接說改成什麼，其他都是你確認過或現有規格寫的。」

結尾問：「⚠️ 的地方有需要改的嗎？沒有的話我就準備建單。」

使用者修改後，更新摘要（被確認的 ⚠️ 拿掉標記），只重貼有變動的段落；全部確認後再貼一次完整版本。

### 6. 交給建單

使用者確認摘要後：

- 只涉及一個專案：開一張單，直接交給 `jira-ticket` skill
- 涉及多個專案：交給 `requirement-split` 規劃每個專案各一張主單與相依關係，再交給 `jira-ticket`

**不可以在使用者確認前建單。**

## 需求摘要格式

```
## 需求摘要：<一句話標題>

**專案**：<KEY>（若涉及多個專案全部列出）

### 背景與目的
### 使用者角色與情境
### 功能描述
### 驗收條件
- AC-1：Given ... When ... Then ...
- AC-2：...
### 例外與錯誤處理
### 畫面需求
### 不做的範圍
### 影響範圍
### 相關規格文件
- `specs/xxx.md`：<關係說明，例如「需修改第 3 節的折扣規則」>
### 決策紀錄
- <討論中做過的重要決定，以及被否決的選項和原因>
```

- 驗收條件用 Given / When / Then，結果要能客觀驗證（具體數字、狀態或畫面）
- 「決策紀錄」很重要：其他人看不到這段對話，這是他們理解「為什麼這樣做」的唯一依據
- 資料來源多的需求，在「功能描述」用表格列出「資料 → 來源」，比逐條文字好讀

## 衝突

發現與現有規格衝突時，一定要指出：「這跟 `specs/xxx.md` 第 N 節的規則衝突：...」。衝突屬於關鍵決策，要問使用者以哪個為準，不可以用 ⚠️ 自行決定。

## 不要做的事

- 不要撰寫規格文件、Test Case 或程式碼，那是後續自動化步驟的工作
- 不要把細節一題一題拿出來問；能定預設值的就定，標 ⚠️
- 不要把預設值偷偷寫進摘要而不標 ⚠️
- 不要建議把需求拆成多張單或 subtask
