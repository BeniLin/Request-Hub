# 執行測試與實測指南（驗證深度 2、3 使用）

目的：執行既有測試（深度 2 以上），以及實際操作系統（深度 3），確認畫面的反應、送出的請求、後端的回應、資料庫的變化，和程式碼讀到的是否一致。

測試與實測都會新增、修改、刪除資料，也可能觸發對外的動作，所以限制比讀程式碼嚴格。

## 執行既有測試前要確認的事（驗證深度 2 以上）

以下每一項都要得到使用者明確的答覆才能執行測試，並記在進度檔。任何一項不確定就不執行，該領域改用驗證深度 1。

1. **測試連到的資料庫**：自己檢查測試的設定實際指向哪裡。必須是記憶體資料庫，或可以丟棄的本機、測試資料庫。指向正式環境、共用環境或看不出來時停止並告知使用者
2. **外部服務**：測試會不會真的呼叫外部系統（訊息推播、寄信、付款、AI 服務、檔案儲存、其他系統的 API）。已經用假的替身取代的才執行；會發出真實呼叫的測試跳過，並在行為清單寫明原因
3. **會產生的檔案與要安裝的東西**：執行測試需不需要安裝套件、會不會在 repo 內產生檔案（虛擬環境、套件、資料庫檔、報表、快取）。安裝要先得到使用者同意；產生的檔案要已被 `.gitignore` 排除，否則改在 repo 外進行或請使用者決定

只執行測試，不修改測試，也不為了讓測試通過而修改程式碼或設定。

## 實測開始前要確認的事（驗證深度 3）

以下每一項都要得到使用者明確的答覆才能開始，並記在進度檔。任何一項不確定就不實測，該領域改用驗證深度 2。

1. **環境**：在哪裡跑。只接受本機或專用的測試環境
2. **資料庫**：連到哪個資料庫。必須是可以丟棄的本機或測試資料庫。啟動前自己檢查設定實際指向哪裡，指向正式環境、共用環境或看不出來時停止並告知使用者
3. **外部服務**：這個領域會呼叫哪些外部系統（訊息推播、寄信、付款、AI 服務、檔案儲存、其他系統的 API）。每一個都要決定：關閉、指向測試帳號、或這部分不實測。**不可以讓實測發出真實的訊息、信件、扣款，或寫入正式的儲存空間**
4. **帳號**：用哪些測試帳號。至少需要一個有權限的與一個沒有權限的，才能驗證權限情境
5. **啟動方式**：會不會在 repo 內產生檔案（虛擬環境、套件、資料庫檔、上傳的檔案）。產生的檔案要已被 `.gitignore` 排除，否則改在 repo 外進行或請使用者決定

## 不可以做的事

- 不對正式環境做任何操作，包含只是登入
- 不修改程式碼來幫助觀察（不加日誌、不改設定檔）。需要的腳本放在 repo 之外的暫存位置
- 不把真實個資、密碼、金鑰、token 寫進文件。範例資料一律自己編
- 不安裝使用者沒同意的工具或套件
- 啟動失敗時不擅自修改環境去修。回報錯誤訊息，由使用者決定

## 可用的觀察方式

依這次對話有的工具選擇，並告訴使用者實際用了哪一種。

| 要觀察的 | 方式 |
|---|---|
| 畫面與操作 | 可以操作瀏覽器的工具，例如 Playwright（點擊、輸入、拖拉、按鍵、截圖）。**沒有這類工具時，前端操作無法實測，也無法拍快照**，保持 `程式碼` 並寫明原因，不要用呼叫 API 冒充操作畫面。工具需要安裝時先得到使用者同意 |
| 送出的請求與回應 | 瀏覽器工具的網路紀錄；或後端的存取紀錄；或直接用指令呼叫 API（只能驗證後端，不能驗證畫面） |
| 資料庫的變化 | 操作前後各查一次相關資料表，比對新增、修改、刪除的列與欄位。相關資料表以行為清單的「資料寫入」為準，另外比對各表的筆數，找出清單沒列到的寫入 |
| 其他結果 | 檔案的出現與消失、快取內容、發出的事件、後端日誌中的錯誤 |
| 既有測試 | 執行測試並記錄結果，這不需要瀏覽器 |

## 畫面快照

畫面快照是實測的長期依據：規格上寫的畫面反應，要有一張圖可以對照。需求變更後，流程會依同樣的重現方式重新拍攝並覆蓋同一個檔案，所以**每張快照都要能被別人照著重拍出來**。

開始前和使用者確認兩件事，並記在進度檔：

1. **視窗大小**：預設 1280×800。系統主要在手機上使用時，改用使用者指定的大小。整個專案用同一個大小，不要中途更換
2. **測試資料**：畫面上會出現的資料（名稱、金額、日期）要是固定的、自己編的測試資料，重拍時才比得出差異

存放與命名：

- 位置：`specs/_screenshots/<領域>/<功能>/`，`<領域>/<功能>` 和規格文件的路徑一致（`specs/member/register.md` 的快照放在 `specs/_screenshots/member/register/`）
- 檔名：`<兩位數序號>-<英文小寫與連字號的簡短描述>.png`，例如 `03-email-format-error.png`。檔名一旦寫進規格就不要改，重拍時覆蓋同一個檔案，舊的畫面留在 git 歷程中
- 格式：PNG，只拍視窗範圍。重點在視窗之外時改拍該元素或整頁，並在重現方式寫明

要拍哪些：

- 每個頁面或視窗的初始狀態（包含沒有資料時的樣子）
- 每個前端操作**之後**的畫面：成功、失敗、處理中各自看得到的結果（訊息、視窗、清單變化、欄位錯誤）
- 權限不同而畫面不同時，每種角色各一張
- 操作前的狀態已經有快照時不用重拍，在規格上指向同一張即可

每張快照都要在規格文件的「畫面快照」表登記：檔案、畫面狀態、重現方式（角色、頁面、前置資料、操作步驟）、會變動的區域、對應的操作或規則、拍攝日期。重現方式要寫到另一個人或自動化流程照著做就能拍出同一個畫面。

不可以做的事：

- 快照中不可以出現真實個資、密碼、金鑰、token。拍之前先看畫面，有的話換成測試資料再拍，換不掉就不拍，並在清單寫明原因
- 不拍正式環境的畫面
- 不修改程式碼或樣式來讓畫面好拍
- 不用舊的、別人給的或其他環境的圖片充當快照。快照一定是這次實測當下拍的
- 拍不到的畫面（處理中的狀態一閃而過、需要真實外部服務才會出現）不要用相近的畫面代替。在規格的「畫面快照」表下方列為未拍攝並寫明原因

會隨時間或執行而改變的內容（現在時間、流水號、隨機排序、動畫）無法固定時，在「會變動的區域」欄寫明是哪一塊，之後比對時才不會誤判。

## 每個操作的實測步驟

1. 記下操作前的狀態：畫面、相關資料表。這個畫面狀態還沒有快照時先拍一張
2. 執行一個操作（一次只做一個，才能對應到結果）
3. 記錄：畫面的反應、送出的請求（方法、路徑、資料）、回應（狀態碼、內容）、資料庫的差異、其他結果。畫面的反應要拍下快照，並記下重現方式
4. 和程式碼追蹤的結果比對：
   - 一致：在行為清單標為 `實測` 與日期
   - 不一致：兩者都記下來，列為未確認事項。不要挑一個當作正確的
   - 發現清單上沒有的行為（多寫了一個資料表、多送了一個請求）：補進清單並追蹤來源
5. 再做下一個操作

情境檢查表中的情境同樣逐一操作：沒有權限的帳號、不合法的輸入、連按兩次、不存在的目標等。會破壞環境的情境（塞滿磁碟、關掉資料庫）不要做，保持 `程式碼`。

同時操作、外部系統失敗這類情境通常難以實測。做得到才做，做不到就保持 `程式碼` 並寫明，不要用推測的結果填上 `實測`。

## 結束時

1. 停止自己啟動的服務與程序
2. 確認 repo 內除了 `specs/` 沒有其他變更（`git status`）。有的話找出來源並告知使用者，不要直接刪除不是自己建立的檔案
3. 逐張打開這次拍的快照檢查：畫面和登記的狀態相符、沒有真實個資或機密、`specs/_screenshots/` 內的每個檔案都登記在規格的「畫面快照」表，表上的每個檔案也都存在
4. 告訴使用者測試資料庫中留下了哪些實測資料，由使用者決定是否重建。快照依賴這些資料才能重拍時，一併說明
5. 在進度檔記錄：實測日期、環境、用了哪些觀察方式、拍了幾張快照、哪些項目無法實測或無法拍攝與原因
