# 規格初始化

目標：讓一個既有專案可以被需求流程使用。需求討論時，Claude 會先讀 `specs/INDEX.md` 決定要看哪些文件，所以索引必須能回答「這個系統有哪些功能、每個功能的規則寫在哪裡」。

大型專案無法一次讀完，所以這個 skill 分階段進行，每個階段結束都停下來讓使用者確認，並把進度寫進檔案，可以跨多次對話接續。

## 總原則

- **只寫 `specs/` 資料夾**，絕對不修改程式碼或其他檔案。實測用的暫存腳本放在 repo 之外
- **不猜測**：程式碼看不出意圖的地方，寫進「未確認事項」，不要自行補上業務理由
- **不寫入機密**：程式碼中的密碼、金鑰、token、連線字串、內部 IP，一律不得出現在文件中。實測時看到的真實個資也不得寫入
- **盤點階段不讀完整個 repo，反推階段要讀完整個領域**：階段 1 用檔案清單、目錄結構、路由、搜尋掌握全貌；階段 3 對選定的領域則要把屬於它的每個檔案完整讀過，不可以只讀搜尋命中的片段
- **靠清單，不靠印象**：階段 3 的每個操作、入口、資料寫入都要先登記在行為清單，再逐項處理。沒有登記的東西等於沒看過
- **每條規則都標明怎麼得知的**：`實測`（實際操作並觀察到結果）、`測試`（既有自動化測試通過且斷言了這個行為）、`程式碼`（只讀過程式碼）。不可以把只讀過程式碼的行為寫成已經驗證
- **實測過的畫面要留下快照**：驗證深度 3 的每個前端操作，都要把看到的畫面存成快照放進 `specs/_screenshots/`，並在規格上登記重現方式。快照是長期依據，需求變更後會依同樣的方式重拍，做法見 `references/runtime-verification.md` 的「畫面快照」
- **不宣稱涵蓋所有情況**：只報告清單上有幾項、處理了幾項、哪些沒處理與原因。沒處理的項目要留在文件裡讓人看得到
- **執行既有測試與實測都只在本機或測試環境進行**，絕對不對正式環境操作。開始前要先得到使用者的確認，細節見 `references/runtime-verification.md`
- 一律使用繁體中文撰寫文件

## 階段 0：準備

1. 確認目前在**專案 repo 的根目錄**（有 `.git`）。如果是 Request-Hub，停止並請使用者改開專案 repo
2. 確認工作目錄沒有未 commit 的變更，有的話請使用者先處理
3. 切到工作分支 `docs/spec-init`。進度檔存在這個分支上，所以**要先切分支，才能判斷是不是接續**。先 `git fetch`，再檢查本機與遠端有沒有這個分支：
   - **沒有**：從最新的主分支建立 `docs/spec-init`。主分支通常有保護，最後要透過 PR 合併
   - **有，而且還沒合併進主分支**：切過去。只有遠端有時建立本機分支來追蹤；兩邊都有時先把遠端的更新拉下來
   - **有，但已經合併進主分支**：告訴使用者，並詢問是否刪除舊分支、從最新的主分支重新建立。使用者同意才刪
4. 檢查 `specs/.init-progress.md` 是否存在：
   - **存在**：這是接續先前的初始化。讀取它與 `specs/.init-inventory/` 內的行為清單，向使用者報告目前進度，從中斷的地方繼續，跳過已完成的階段。已完成的領域中有標為 `實測` 卻沒有快照的前端操作時（舊版流程不拍快照），列出這些領域並問使用者是否補拍。補拍只重做步驟 3.5 的畫面操作與快照，並更新規格的「畫面快照」段落，不重做清單與追蹤；補拍時看到的畫面和規格寫的不一樣，就列為未確認事項
   - **不存在**：新的初始化，繼續下一步
5. 檢查 `specs/INDEX.md` 是否已存在。存在的話問使用者：**重建**（以盤點結果重新產生）或**補充**（保留現有內容，只加入遺漏的部分）

## 階段 1：盤點

依照 `references/survey-guide.md` 盤點 repo，重點是**找出功能領域**，不是列出所有檔案。

盤點項目：

1. **規模**：依副檔名統計檔案數，排除第三方套件與建置產物
2. **技術棧與入口**：使用的語言、框架，以及使用者從哪裡進入系統（頁面、API、排程、背景工作、n8n workflow 等）
3. **功能領域**：依照業務功能（不是技術分層）切分，例如「會員」「報價」「選股」「通知」。每個領域記錄：
   - 一句話說明
   - 主要程式碼位置
   - 入口數量（頁面數、API 數等）
   - 已有的文件（若有）
   - 近一年的修改頻率（用 git log 統計）
4. **既有文件**：repo 內所有說明文件、API 規格（OpenAPI／Swagger）、資料表定義、README 中的規則說明。記錄它們在不在 `specs/` 或 `docs/` 內
5. **實測條件**：系統能不能在本機或測試環境啟動（啟動方式、需要的資料庫與外部服務）、有哪些自動化測試與執行方式、這次對話有沒有可以操作瀏覽器的工具。只記錄，不在這個階段啟動

把盤點結果寫進 `specs/.init-progress.md`（格式見 `templates/progress.md`），然後向使用者報告：

- 功能領域清單（表格），依修改頻率由高到低排序
- 既有文件的位置與狀況
- 實測條件
- 你建議的處理範圍與驗證深度

向使用者說明數字的來源與限制（例如路由數是文字比對的粗估），不要把粗估寫成精確數字。

並請使用者確認四件事：

1. **領域切分是否正確**（要合併、拆開或改名的）
2. **處理範圍**：
   - A. 只建立索引：已有的文件列進索引，沒有文件的領域列在「尚未文件化」
   - B. 索引 + 反推現況規格：對選定的領域，清點所有操作、API、後端行為與資料寫入，寫成規格。領域已有文件時仍然可以選 B，既有文件會拿來和程式碼比對
3. 選 B 的話，**要反推哪些領域、順序為何**。建議從修改最頻繁的領域開始，因為那裡最常有新需求
4. 選 B 的話，**驗證深度**：
   - 1. 只讀程式碼：所有規則標為 `程式碼`
   - 2. 讀程式碼 + 執行既有測試：有測試佐證的規則標為 `測試`。測試也可能寫入資料庫或呼叫外部服務，需要使用者確認測試連到哪裡（見 `references/runtime-verification.md` 的「執行既有測試前要確認的事」）
   - 3. 再加上實際操作：在本機或測試環境啟動系統，操作畫面、觀察 API 與資料庫的變化，並留下畫面快照。需要使用者確認環境、資料庫與外部服務的處理方式（見 `references/runtime-verification.md` 的「實測開始前要確認的事」）。只有深度 3 會產生畫面快照

   驗證深度 3 的工作量遠大於 1，一個領域可能需要多次對話。如實告訴使用者，讓使用者依領域決定深度。

既有文件放在 `specs/`、`docs/` 以外的位置時，提醒使用者：需求流程只讀得到允許的資料夾，建議搬進 `specs/`。搬移屬於程式碼 repo 的結構調整，**請使用者自行決定並操作**，你不要搬。

## 階段 2：建立索引

依確認後的盤點結果，使用 `templates/INDEX.md` 建立 `specs/INDEX.md`：

- 已有規格文件的領域：每份文件一行，「涵蓋內容」要寫出具體的規則與關鍵字，讓人看到需求中的詞就能對應到文件。寫之前要實際讀過該文件，不要只看檔名
- 沒有文件的領域：列在「尚未文件化的功能」，寫出這個領域做什麼、包含哪些主要功能。這讓需求討論時 Claude 知道這個功能存在、但沒有規格可參考，會改為多問使用者

完成後 commit：`docs: 建立規格索引`，更新進度檔，向使用者報告。

使用者選擇範圍 A 時，直接跳到階段 4。

## 階段 3：反推現況規格（逐個領域進行）

**一次只處理一個領域**，處理完就停下來讓使用者檢查。大型領域要再拆成功能（例如一個頁面或一組相關 API），一次對話處理幾個功能，其餘留在行為清單中下次接續。

每個領域依序做以下步驟。步驟 3.1 到 3.4 的做法、搜尋方式與情境檢查表見 `references/behavior-inventory.md`。

### 3.1 建立行為清單

使用 `templates/inventory.md` 建立 `specs/.init-inventory/<領域>.md`，登記這個領域的：

1. **檔案**：屬於這個領域的每個檔案（前端頁面與元件、模板、腳本、路由、服務、資料模型、migration、測試）。之後每個檔案都要完整讀過並打勾
2. **前端操作**：使用者在畫面上能做的每個動作，包含點擊、雙擊、右鍵、拖拉、鍵盤快速鍵、輸入與選取、表單送出、貼上、上傳、捲動、觸控，以及不需要使用者動作就發生的行為（載入時、定時、收到推播時）
3. **後端入口**：每個 API 與頁面路由，以及非使用者觸發的入口（排程、webhook、訊息佇列、啟動時執行、指令）
4. **資料寫入**：每一處新增、修改、刪除資料庫的程式，以及其他會留下結果的動作（寫檔案、更新快取、呼叫外部系統、發送通知或事件）

登記時只記「有這一項」與位置，先不分析。搜尋只是找線索，**以完整讀過檔案為準**，因為事件委派、動態產生的元素、共用元件都搜尋不到。

清單完成後 commit：`docs: 建立 <領域> 行為清單`，向使用者報告各類有幾項。項目很多時，請使用者確認要全部處理還是先做哪些功能。

### 3.2 逐項追蹤

對清單上的每個前端操作，往下追到底並記錄：

- 觸發條件（什麼時候按鈕可以按、什麼權限才看得到）
- 畫面的反應（包含處理中、成功、失敗各自顯示什麼）
- 送出哪個 API、帶什麼資料
- 後端做了哪些檢查，依什麼順序
- 寫入哪些資料表的哪些欄位，是不是在同一個交易中，失敗時會不會回復
- 連帶的結果（快取、事件、通知、檔案、連動刪除、自動填入的欄位）
- 回應的內容與畫面如何更新

沒有畫面的入口（排程、webhook 等）從入口開始做同樣的追蹤。

### 3.3 套用情境檢查表

對每個功能，逐類檢查 `references/behavior-inventory.md` 的情境檢查表（權限、輸入、資料狀態、重複與同時操作、資料量、外部系統失敗、部分失敗、畫面操作方式等）。每一類要有結論：

- 這個情境下系統目前的行為（附來源）
- 或「不適用」與原因
- 或「程式碼沒有處理這個情況」，寫進未確認事項

不可以略過不寫。每一類的結論記在行為清單的「情境檢查」表；寫規格時，有實際行為的寫成業務規則，不適用的在規格裡合併成一行說明。

### 3.4 閉合檢查

用清單互相對照，找出遺漏：

- 每個前端送出的 API 都對得到後端入口
- 每個後端入口都有呼叫端（前端操作、排程、外部系統），找不到的列為未確認事項
- 每個資料表至少有一處寫入，或說明資料從哪裡來
- 這個領域的每個檔案都已完整讀過
- 既有文件提到的每個功能都在清單上；文件與程式碼不一致的地方列為未確認事項，不要判斷誰對

### 3.5 驗證

依使用者選的驗證深度：

- **深度 2 以上**：先完成 `references/runtime-verification.md` 的「執行既有測試前要確認的事」，再執行這個領域的既有測試，記錄通過與失敗。測試通過且斷言了該行為，才標為 `測試`。失敗的測試如實記錄，不要修
- **深度 3**：依 `references/runtime-verification.md` 實際操作。每個操作記錄實際看到的畫面反應、送出的請求與回應、資料庫前後的差異，並依「畫面快照」一節把畫面存進 `specs/_screenshots/<領域>/<功能>/`。**實測結果和程式碼讀到的不一樣時，兩者都寫下來並列為未確認事項**

沒辦法實測的項目（沒有瀏覽器工具、需要真實的外部服務、環境啟動不了）保持 `程式碼`，並在清單上寫明原因。實測了但拍不到快照的畫面同樣要寫明原因。不要因為做不到就略過不提。

### 3.6 撰寫規格

1. **規劃文件**：一個領域通常拆成多份文件，每份對應一個功能（例如 `specs/member/register.md`、`specs/member/level.md`）。單份文件超過約 300 行就應該再拆
2. **撰寫**：使用 `templates/as-is-spec.md`。規則要寫成業務語言（「金卡會員打 9 折」），不是程式語言（「if level == 3 then price * 0.9」），每條規則標註來源程式碼位置與驗證方式
   - **每件事只寫一次**：欄位驗證與錯誤訊息、各種情況下的行為、交易與失敗時的結果都寫成「業務規則」裡的規則；「畫面操作」與「後端入口與資料寫入」兩張表只填規則編號，不重複描述
   - 單純的導覽操作（切換分頁、取消、回列表）在「畫面操作」合併成一行，不逐列寫；行為清單上仍然逐項登記
   - 行為清單已經逐項列出的內容（每個操作、入口、寫入的位置）不用在規格再抄一次，規格只寫讀者需要知道的行為
3. **登記快照**：驗證深度 3 時，把每張快照填進規格的「畫面快照」表（檔案、畫面狀態、重現方式、會變動的區域、對應的操作或規則、拍攝日期），「畫面操作」表的每個 `實測` 項目都要指到至少一張快照，或寫明為什麼沒有
4. **標示不確定的地方**：看起來像 bug、互相矛盾、意圖不明的邏輯，寫進「未確認事項」，不要擅自判斷哪個才是對的
5. 在行為清單上，把每個項目標上寫進了哪份文件。**清單上每一項都要有去處**：寫進規格、列為未確認事項，或標為未處理並寫明原因

### 3.7 更新索引、commit、報告

1. **更新索引**：把這個領域列進正式的分類，「涵蓋內容」後加上「（現況反推，待確認）」。這個領域原本列在「尚未文件化的功能」時，把那一列移除，同一個領域不要出現兩次。領域只反推了一部分功能時，還沒反推的功能留在「尚未文件化的功能」
2. **commit**：`docs: 反推 <領域> 現況規格`，更新進度檔的覆蓋數字。這個領域的快照和規格放在同一個 commit
3. **向使用者報告**：
   - 產出了哪些文件
   - 覆蓋數字：前端操作、後端入口、資料寫入各有幾項，其中 `實測`、`測試`、`程式碼`、未處理各幾項
   - 快照數字：拍了幾張、`實測` 的前端操作中有幾項沒有快照與原因
   - 未處理的項目與原因
   - 未確認事項有幾項，最值得注意的幾項
   - 提醒這些文件需要熟悉該功能的人確認，並詢問要繼續下一個領域，還是先停在這裡

如果環境支援子代理（subagent），可以把「讀檔案、登記清單、追蹤」交給子代理平行處理多個領域，但實測、撰寫與更新索引仍在主對話中逐一完成，避免索引被同時修改、實測資料互相干擾。

## 階段 4：收尾

1. 再讀一次 `specs/INDEX.md`，確認所有路徑都存在、沒有遺漏。`specs/_screenshots/` 不列進索引，但要確認規格中提到的每個快照檔都存在
2. 進度檔與行為清單處理：
   - 所有計畫的領域都已完成，且清單上每一項都有去處：問使用者是否刪除 `specs/.init-progress.md` 與 `specs/.init-inventory/`。使用者想留著行為清單當作檢查依據時就保留
   - 還有領域或項目沒做：保留，下次執行這個 skill 會自動接續
3. 確認實測留下的東西已清理：啟動的服務已停止，repo 內除了 `specs/` 沒有其他變更
4. 問使用者是否要推送分支並開 PR。同意後執行 `git push -u origin docs/spec-init`，並用 `gh pr create` 開 PR，標題 `docs: 規格初始化`，說明中列出：建立的文件、處理範圍、驗證深度與覆蓋數字、待確認事項總數
5. 提醒使用者：
   - PR 合併到主分支後，需求流程才讀得到
   - 「現況反推，待確認」的文件，請熟悉該功能的人確認後，移除該標記
   - 之後新增的規格由流程中的步驟 3 自動維護索引
   - `specs/_screenshots/` 的快照是這次實測當下的畫面。之後需求變更時要依規格上的重現方式重拍並覆蓋同一個檔案，否則快照會和實際畫面脫節

## 中斷與接續

任何時候使用者要停下來，都先更新 `specs/.init-progress.md` 與行為清單並 commit，確保下次能接續。不要留下未 commit 的半成品。實測進行到一半時，先停止啟動的服務再結束。
