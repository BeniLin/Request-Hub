# 步驟 6：實作（Jira C → E）

這個 skill 負責流程中「C 待實作 → E 待驗證」這一段。此時規格、Test Case 都由人確認過，測試腳本也已經寫好。你的工作是**寫出符合規格、能讓那些測試通過的程式**。

你會在無人看管的排程中執行，沒有人可以回答問題或按確認，所以每個動作都要保守、可重跑：寧可回報問題，也不要猜。

最重要的原則：**規格與測試是標準，你不能改標準**。`specs/` 與 `tests/e2e/` 你只能讀。覺得規格做不到、或測試寫錯時，回報給人，不要自己調整，也不要用繞過測試的方式讓它通過。

## 0. 設定（第一次使用前由管理者填寫）

| 常數 | 值 | 說明 |
|---|---|---|
| REQUEST_HUB_REPO | `BeniLin/Request-Hub` | 讀取專案設定的來源 repo |
| STATUS_FROM | `C 待實作` | 要處理的 Jira 狀態，必須與 Jira 上的名稱完全相同 |
| STATUS_TO | `E 待驗證` | 完成後轉換到的狀態 |
| STATUS_PROBLEM | `D 待人工處理` | 需要人回答或介入時轉換到的狀態 |
| RETRY_FIELD | `退回次數` | 記錄被退回幾次的數字欄位 |
| MAX_RETRY | `3` | 退回次數超過這個值就不再實作，交給人 |
| MAX_TICKETS_PER_RUN | `1` | 每次執行最多處理幾張主單。實作耗時較長，預設一次一張 |
| LOCK_TIMEOUT | `4h` | 鎖超過多久視為卡住、可以回收 |
| PROJECT_BASE_BRANCH | `develop` | 專案 repo 的基準分支 |

啟動這次執行的提示詞如果指定了更少的處理張數，以提示詞為準；提示詞不可以放寬其他任何規則。

專案清單每次執行時從 REQUEST_HUB_REPO 的 `main` 讀取：`projects/registry.csv` 與 `projects/<KEY>.md`。讀不到 registry 時，整次執行直接停止並回報。

你可以修改與不可以修改的範圍：

| 路徑 | 規則 |
|---|---|
| `specs/` | **只能讀**。步驟 3 的範圍 |
| `tests/e2e/` | **只能讀**。步驟 5 的範圍 |
| `changes/` | 不要動。步驟 10 的範圍 |
| `docs/` | 可以修改，用來更新實作細節與操作說明 |
| 其他（原始碼、單元測試、資料庫 migration、設定範本） | 可以修改 |

## 0.5 判斷執行環境

依序判斷：

1. 啟動的提示詞寫明是「雲端 Routine」→ 雲端模式
2. 有 `add_repo` 工具可用 → 雲端模式
3. 目前的工作目錄是某個專案 repo 的本機 clone → 本機模式
4. 都不符合 → 停止並回報

### 雲端模式的規則

1. 在工作目錄及其上下層尋找已 clone 的 git repo，用 `git remote get-url origin` 建立「repo 名稱 → 本機路徑」的對照
2. 在 REQUEST_HUB_REPO 的 clone 中 `git fetch origin main`，用 `git show origin/main:projects/registry.csv` 讀取 registry。對 Request-Hub 只讀不寫
3. registry 中的專案，其 repo 已經 clone 才列入本次處理範圍。沒有 clone 時：有 `add_repo` 工具就掛載（`access: "push"`）；沒有就跳過該專案，不查詢也不鎖定它的票，在報告的「未處理的專案」列出。找不到 `add_repo` 不是錯誤
4. clone 可能只包含預設分支，需要的分支要明確 `git fetch origin <分支>`
5. push 被拒絕時，這張票視為失敗，在報告中原樣附上錯誤訊息，不要改用其他分支名稱繞過
6. `gh auth status` 顯示 invalid 是正常的，不要嘗試修復
7. 每張票處理完，把該 repo 切回 PROJECT_BASE_BRANCH 並確認工作目錄乾淨

### 本機模式的規則

1. 只處理目前這個 repo 對應的專案，JQL 只查這一個專案
2. registry 用 `gh api` 從 REQUEST_HUB_REPO 的 `main` 讀取
3. 開始前確認工作目錄乾淨，有未 commit 的修改就停止並回報
4. 每張票處理完，切回原本所在的分支

## 1. 撈單

```
project in (<KEYS>)
AND status = "C 待實作"
AND issuetype not in subTaskIssueTypes()
AND ("處理中" is EMPTY OR "處理中" < -4h)
ORDER BY priority DESC, created ASC
```

狀態名稱使用 STATUS_FROM 的值，時間使用 LOCK_TIMEOUT 的值。只取前 MAX_TICKETS_PER_RUN 張。查不到任何票就回報「本次無待處理單」並結束。查詢回報狀態不存在時，停止整次執行並回報，不要改用相近的名稱。

## 2. 逐張處理

任何一步失敗，照「失敗處理」收尾，然後繼續下一張。

### 2.1 鎖單與重試上限

把「處理中」欄位寫成目前時間。寫入失敗就跳過這張。

讀取 RETRY_FIELD 的值（空值視為 0）。**大於 MAX_RETRY 時不要實作**：依 2.10 回報，說明「已被退回 N 次，需要人檢視需求、規格或測試是否有問題」，並附上歷次退回原因的摘要。

### 2.2 讀取單子，判斷這次的類型

讀主單的描述與**所有留言**，找出最新一則決定這次工作內容的留言：

| 類型 | 判斷方式 | 這次要做什麼 |
|---|---|---|
| 第一次 | 沒有任何【實作完成】留言 | 依規格完成全部實作 |
| 驗證失敗 | 最新的是【驗證失敗】（步驟 8） | 依失敗原因與未通過的測試修正 |
| 審查退回 | 最新的是【審查退回】F 或 H 關卡 | 逐條處理審查意見 |
| 合併失敗 | 最新的是【合併失敗】（步驟 12） | 解決與基準分支的衝突，或修正合併後才失敗的測試 |
| 人工回覆 | 最新的是【人工回覆】 | 依回覆內容繼續先前卡住的工作 |

不是第一次時，重點是**針對問題修正**，不要重寫已經通過審查的部分。

### 2.3 切換到分支並同步基準分支

1. `git fetch origin feature/<單號>` 後切換過去。**分支必須已經存在**。不存在時視為失敗，不要自己建立
2. `git fetch origin <PROJECT_BASE_BRANCH>`，把 `origin/<PROJECT_BASE_BRANCH>` 合併進目前分支（使用 merge，不要 rebase）
3. 合併有衝突時：
   - 衝突的檔案**不包含** `specs/`、`tests/e2e/`、`changes/`：解決衝突。兩邊的修改都要保留其意圖，不可以為了省事直接捨棄基準分支上別人的修改。解決後完成 merge commit
   - 衝突的檔案**包含** `specs/`、`tests/e2e/` 或 `changes/`：`git merge --abort`，依 2.10 回報。這代表另一張單改了同一份規格或測試，需要人決定
4. 同步之後，檢查這張單新增的東西有沒有和基準分支新進來的內容「接不上」，即使 git 沒有回報衝突。最常見的是**資料庫 migration**：這張單的 migration 和基準分支新增的 migration 如果接在同一個上一版後面，合併後會出現兩個最新版本（多個 head），系統會無法啟動。這時把這張單的 migration 改接在基準分支最新的 migration 之後，並用專案的工具確認只剩一個最新版本。只能調整這張單自己新增的 migration，不可以修改基準分支上已經存在的
5. 最新的【驗證失敗】或【合併失敗】留言如果寫著「分支無法部署到驗證環境」，原因在留言附上的部署記錄裡（例如 migration 錯誤、建置失敗、服務啟動失敗）。依記錄找出原因並修正；記錄顯示的問題明顯與這張單的程式無關時（例如連接埠被佔用、磁碟空間不足、外部服務連不上），不要修改程式，依 2.10 回報
6. 最新的【驗證失敗】留言顯示絕大多數的測試都失敗、而且錯誤訊息相同時，先判斷是不是共同的原因。錯誤發生在登入、開啟網址、建立測試的前置資料這類「還沒測到本單功能」的步驟時，問題通常在測試環境或測試帳號，不在程式：不要為了讓測試通過去修改登入、權限或無關的程式，依 2.10 回報，說明錯誤訊息與你判斷的原因。只有在錯誤確實指向本單的程式時才修改

### 2.4 讀取標準

在分支上依序閱讀：

1. 步驟 3 的【規格完成】留言列出的規格檔案：規則、**Test Case**、**預期畫面**
2. `tests/e2e/<單號>/README.md`：對照表與執行需求
3. `tests/e2e/<單號>/selectors.ts`：**這張單新增的畫面元素必須加上這裡定義的 `data-testid`**，名稱要完全相同
4. `tests/e2e/<單號>/` 的測試腳本：了解測試會怎麼操作畫面、檢查什麼。實作時要讓這些操作成立
5. `projects/<KEY>.md` 的注意事項，以及專案 repo 中的開發說明（例如 README、開發指南、`CLAUDE.md`）

規格文件中的「待確認事項」還有內容時，代表規格尚未定案：不要實作，依 2.10 回報。「已採用的假設」段落不算待確認事項：那些做法已經寫進規則並由人確認過，照常實作。

### 2.5 了解專案

實作之前先了解這個專案怎麼寫：

- 找出與這次需求最相近的既有功能，閱讀它的程式、單元測試與文件，**沿用相同的結構、命名、錯誤處理與寫法**
- 從專案的說明文件找出**單元測試怎麼執行**。優先順序：`projects/<KEY>.md` → 專案 repo 的開發說明 → 套件設定檔中的測試指令。不要自己發明指令
- 資料表結構要變更時，使用專案既有的 migration 機制，不要手寫沒有被納管的 SQL

### 2.6 實作

依規格的規則逐條進行：

- **只做規格寫的事**。規格「不做的範圍」列出的內容不要做；規格沒提到的功能、順手的重構、無關的格式調整都不要做
- 每一條規則都要落實，包含例外與錯誤處理、權限檢查、輸入驗證。不要只做成功的情境
- 畫面上的文字（標題、按鈕、錯誤訊息）使用規格寫的文字，一字不差。測試會檢查這些文字
- 新增的畫面元素加上 `selectors.ts` 定義的 `data-testid`
- **撰寫單元測試**：為新增與修改的邏輯補上單元測試，放在專案既有的測試位置，寫法比照既有測試。既有的單元測試因為行為依規格改變而失敗時，更新它；與這次需求無關的單元測試失敗時，不要為了通過去修改它，先找出原因
- 需要更新操作說明或開發文件時，修改 `docs/`。主單描述中「相關規格文件」提到要同步更新的 `docs/` 文件，在這裡處理
- 不要寫入任何密碼、金鑰、token 或內部網址。設定值沿用專案既有的設定方式

**絕對不可以為了讓測試通過而做的事**：偵測測試環境並改變行為、把測試檢查的值寫死、只在特定輸入時回傳預期結果。測試檢查的是規格描述的行為，程式要真的具備那個行為。

### 2.7 執行單元測試

依 2.5 找到的方式安裝相依套件並執行專案的單元測試：

- 全部通過才繼續
- 有失敗：修正後重跑。同一個問題修了三次仍然失敗，依 2.10 回報，附上錯誤訊息與你嘗試過的做法
- **環境無法安裝套件或無法執行**（例如缺少系統函式庫、連不到套件來源）：不要因此卡住。照常進行後續步驟，並在 Jira 留言與執行報告中明確註明「單元測試未執行」與原因。步驟 8 會在 Jenkins 上執行自動化測試

**不要執行 `tests/e2e/` 的測試**。這裡沒有部署好的系統，那是步驟 8 的工作。

### 2.8 檢查與 commit

1. **範圍檢查**：`git status --porcelain` 與 `git diff --name-only`，確認沒有動到 `specs/`、`tests/e2e/`、`changes/`。有的話還原那些變更
2. **內容檢查**：看過自己的完整 diff，確認沒有除錯用的輸出、被註解掉的舊程式、無關的修改、機密資訊
3. **對照檢查**：逐條對照規格的規則與 `selectors.ts`，確認每一條都有對應的實作、每一個 `data-testid` 都已加上
4. commit 訊息：
   - 第一次：`feat(<單號>): <一句話摘要>`
   - 修正：`fix(<單號>): <一句話摘要>`
   - 只改文件：`docs(<單號>): <一句話摘要>`
   - **不可以**用 `spec(` 或 `test(` 開頭。這兩個前綴保留給步驟 3 與步驟 5，步驟 8 會依此檢查
   - 可以分成多個 commit，每個都要符合上述格式
5. push 到 `origin feature/<單號>`。不要 force push

### 2.9 開立 PR

檢查 `feature/<單號>` 到 PROJECT_BASE_BRANCH 是否已經有開啟中的 PR：

- 已經有：不要重複開，沿用它
- 沒有：開立一個。標題 `<單號> <主單標題>`，說明包含 Jira 單連結、變更摘要、對應的規格檔案
- 環境沒有可以開立 PR 的工具或權限：不要因此卡住，在 Jira 留言中註明「未能開立 PR，請手動開立」，照常繼續

不要 merge PR，不要指定審查人以外的任何設定。

### 2.10 回報問題（轉到 STATUS_PROBLEM）

需要人回答或介入時：

1. 已經完成、沒有疑問的部分照常 commit 並 push，不要丟棄
2. 重新讀取票的狀態，仍是 STATUS_FROM 才繼續
3. 新增留言：

```
【回報問題】步驟 6（實作）

**摘要**：<給人看的。用一到三句白話說明這次卡在哪裡、需要人決定什麼、結果如何、接下來需不需要人處理（不需要就寫「不需要處理」）。不寫檔名、commit 編號與技術用語>

---

無法完成實作，需要確認以下事項：

1. <位置或規則編號>：<問題>。可能的做法：(a) ... (b) ...
2. ...

已完成的部分：<摘要與分支連結>

回覆後請依情況轉換：需求或 Test Case 要改 → A；測試腳本要修 → T；只需說明做法 → C
```

4. 轉換到 STATUS_PROBLEM，清空「處理中」

以下情況一定要回報，不要自行決定：

- 規格的規則互相矛盾，或與既有功能的行為衝突而規格沒有說明
- 規格要求的事在現有架構下做不到，或需要規格沒提到的重大變更（例如新增外部服務、改變既有資料的意義）
- 認為測試腳本有誤：測試的操作方式不可能成立，或斷言與 Test Case 的預期結果不一致。說明是哪一個測試、為什麼
- 需要人提供的東西：金鑰、外部系統的設定、設計稿、決定

### 2.11 寫回前再確認

重新讀取票的狀態：

- 仍是 STATUS_FROM → 繼續
- 已被改成其他狀態 → 放棄寫回：不轉換、不留完成的留言，只清空「處理中」，在報告中註明。已 push 的內容保留

### 2.12 寫回 Jira

新增留言：

```
【實作完成】步驟 6（自動化）

**摘要**：<給人看的。用一到三句白話說明這次做了或修正了什麼、結果如何、接下來需不需要人處理（不需要就寫「不需要處理」）。不寫檔名、commit 編號與技術用語>

---

**分支**：<分支連結>（commit <短雜湊>）
**PR**：#<編號> <連結>（或「未能開立 PR，請手動開立」）

**這次的類型**：<第一次 / 驗證失敗修正 / 審查退回修正 / 合併失敗修正 / 人工回覆後繼續>

**變更摘要**
- <做了什麼，用功能的角度描述>

**修改的檔案**
- <檔案路徑>：<一句話說明>

**單元測試**：<新增 n 個、全部通過 / 未執行與原因>

**與基準分支同步**：<無衝突 / 已解決衝突：檔案清單與處理方式>

**文件**：<更新了哪些 docs/，或「無」>

**提醒審查的地方**（沒有則寫「無」）
- <實作時做的判斷、規格沒有明講而採用的做法>
```

不是第一次時，另外逐條說明如何回應退回的每一項原因。

然後取得可用的轉換清單，選擇目標狀態為 STATUS_TO 的那一個。最後清空「處理中」。

## 3. 失敗處理

流程本身出錯（工具失敗、push 被拒絕、Jira 寫入失敗）時：

1. 在票上留言說明失敗在哪一步、錯誤訊息
2. 清空「處理中」
3. 不要轉換狀態
4. 記入報告的失敗清單

同一張票的留言中已經有 3 次以上連續的失敗紀錄時，不要再處理，在報告中標註「需人工介入」。

## 4. 執行報告

```
## 步驟 6 執行報告 <日期時間>

執行環境：<雲端 / 本機>
查詢到：<N> 張（本次處理 <M> 張，其餘留待下次）
```

## 5. 絕對不做的事

- 不修改 `specs/`、`tests/e2e/`、`changes/`
- 不使用 `spec(` 或 `test(` 開頭的 commit 訊息
- 不用任何方式讓測試「看起來通過」：跳過測試、偵測測試環境、寫死預期值
- 不實作規格以外的功能，不做無關的重構
- 不刪除或停用既有的單元測試來讓建置通過
- 不寫入密碼、金鑰、token、內部網址
- 不 push 到 `main` 或基準分支、不建立新分支、不 merge PR、不刪除分支、不 force push、不 rebase 已經推送的分支
- 不部署，不執行會改動任何實際環境資料的指令
- 不執行 STATUS_FROM → STATUS_TO、STATUS_FROM → STATUS_PROBLEM 以外的任何 Jira 轉換
- 不作廢任何單子，不修改 subtask（舊的單底下可能還有，不需要理會）
- 不修改票的描述、優先度、負責人、退回次數
- 不修改 Request-Hub 的任何內容
