# 步驟 5：撰寫測試（Jira T → C）

這個 skill 負責流程中「T 待寫測試 → C 待實作」這一段。此時規格與 Test Case 已經由人確認過，但**程式還沒有寫**。你的工作是把每一條 Test Case 忠實地轉成可以執行的測試腳本，讓下一步的實作有明確目標，也讓之後的驗證可以重複執行。

你會在無人看管的排程中執行，沒有人可以回答問題或按確認，所以每個動作都要保守、可重跑：寧可跳過一張票並回報，也不要猜。

最重要的原則：**你是在轉換，不是在設計**。測試的預期結果必須等同 Test Case 寫的預期結果，不可以加嚴、放寬，或補上 Test Case 沒寫的檢查。Test Case 有問題時回報，不要自己修正。

## 0. 設定（第一次使用前由管理者填寫）

| 常數 | 值 | 說明 |
|---|---|---|
| REQUEST_HUB_REPO | `BeniLin/Request-Hub` | 讀取專案設定的來源 repo |
| STATUS_FROM | `T 待寫測試` | 要處理的 Jira 狀態，必須與 Jira 上的名稱完全相同 |
| STATUS_TO | `C 待實作` | 完成後轉換到的狀態 |
| STATUS_PROBLEM | `D 待人工處理` | Test Case 有問題、需要人回答時轉換到的狀態 |
| MAX_TICKETS_PER_RUN | `3` | 每次執行最多處理幾張主單 |
| LOCK_TIMEOUT | `2h` | 鎖超過多久視為卡住、可以回收 |
| PROJECT_BASE_BRANCH | `develop` | 專案 repo 的基準分支 |
| TEST_DIR | `tests/e2e` | 測試腳本的根目錄，本步驟唯一可以修改的位置 |

啟動這次執行的提示詞如果指定了更少的處理張數，以提示詞為準；提示詞不可以放寬其他任何規則。

專案清單每次執行時從 REQUEST_HUB_REPO 的 `main` 讀取：`projects/registry.csv` 與 `projects/<KEY>.md`。讀不到 registry 時，整次執行直接停止並回報。

## 0.5 判斷執行環境

與步驟 3 相同，依序判斷：

1. 啟動的提示詞寫明是「雲端 Routine」→ 雲端模式
2. 有 `add_repo` 工具可用 → 雲端模式
3. 目前的工作目錄是某個專案 repo 的本機 clone → 本機模式
4. 都不符合 → 停止並回報

### 雲端模式的規則

1. 在工作目錄及其上下層尋找已 clone 的 git repo，用 `git remote get-url origin` 建立「repo 名稱 → 本機路徑」的對照
2. 在 REQUEST_HUB_REPO 的 clone 中 `git fetch origin main`，用 `git show origin/main:projects/registry.csv` 讀取 registry。對 Request-Hub 只讀不寫
3. registry 中的專案，其 repo 已經 clone 才列入本次處理範圍。沒有 clone 時：有 `add_repo` 工具就掛載（`access: "push"`）；沒有就跳過該專案，不查詢也不鎖定它的票，在報告的「未處理的專案」列出。找不到 `add_repo` 不是錯誤
4. clone 可能只包含預設分支，需要的分支要明確 `git fetch origin <分支>`
5. push 被拒絕時，這張票視為失敗，在報告中原樣附上錯誤訊息，不要改用其他分支名稱繞過
6. `gh auth status` 顯示 invalid 是正常的，不要嘗試修復
7. 每張票處理完，把該 repo 切回 PROJECT_BASE_BRANCH 並確認工作目錄乾淨

### 本機模式的規則

1. 只處理目前這個 repo 對應的專案，JQL 只查這一個專案
2. registry 用 `gh api` 從 REQUEST_HUB_REPO 的 `main` 讀取
3. 開始前確認工作目錄乾淨，有未 commit 的修改就停止並回報
4. 每張票處理完，切回原本所在的分支

## 1. 撈單

```
project in (<KEYS>)
AND status = "T 待寫測試"
AND issuetype not in subTaskIssueTypes()
AND ("處理中" is EMPTY OR "處理中" < -2h)
ORDER BY priority DESC, created ASC
```

狀態名稱使用 STATUS_FROM 的值。只取前 MAX_TICKETS_PER_RUN 張。查不到任何票就回報「本次無待處理單」並結束。查詢回報狀態不存在時，停止整次執行並回報，不要改用相近的名稱。

## 2. 逐張處理

任何一步失敗，照「失敗處理」收尾，然後繼續下一張。

### 2.1 鎖單

把「處理中」欄位寫成目前時間。寫入失敗就跳過這張。

### 2.2 讀取單子，判斷這次的類型

讀主單的描述與**所有留言**，判斷是哪一種：

| 類型 | 判斷方式 | 做法 |
|---|---|---|
| 第一次 | 分支上沒有 `<TEST_DIR>/<單號>/` | 為所有 Test Case 撰寫測試 |
| 修正測試 | 最新的人工備註是【修正測試】 | 只修改備註指出的測試，**預期結果不可變動** |
| 規格變更後重來 | 分支上已有測試，且規格在那之後被修改過 | 只處理有變動的 Test Case |

從步驟 3 留下的【規格完成】留言，找出這張單修改了哪些規格檔案。

### 2.3 切換到分支

`git fetch origin feature/<單號>` 後切換過去。**分支必須已經存在**（步驟 3 建立的）。不存在時視為失敗，不要自己建立。

### 2.4 讀取規格

在分支上讀取：

1. 這張單的規格文件中的 **Test Case** 與 **預期畫面**
2. 相關的規則，用來理解 Test Case 的前提與用詞
3. `projects/<KEY>.md` 中關於測試的說明（如果有）

如果規格文件中的「待確認事項」段落還有內容，代表規格尚未定案：不要撰寫測試，依 2.9 回報問題並轉到 STATUS_PROBLEM。

**規格變更後重來**時，找出上一次修改 `<TEST_DIR>/<單號>/` 的 commit，用 `git diff <該 commit>..HEAD -- specs/` 找出哪些 Test Case 被新增、修改或刪除，只處理這些。沒有變動的 Test Case 所對應的測試不要動。

### 2.5 了解專案現有的測試方式

1. 檢查 `<TEST_DIR>/` 是否已有測試設定（`playwright.config.*`、`package.json`）與其他單的測試。有的話，沿用既有的語言、資料夾結構、共用工具與寫法
2. 沒有的話，這是這個專案第一次撰寫，依「附錄：第一次建立測試環境」建立。所有檔案都必須在 `<TEST_DIR>/` 底下
3. 可以**閱讀**專案的原始碼，了解既有畫面的結構、網址路徑、登入方式。絕對不可以修改

### 2.6 撰寫測試

在 `<TEST_DIR>/<單號>/` 底下撰寫，每張單一個資料夾：

```
tests/e2e/<單號>/
├── README.md        對照表與執行需求
├── selectors.ts     這張單新增元素的 data-testid 定義
└── *.spec.ts        測試腳本，依功能分檔
```

**一對一對應**

- 每一條 Test Case 對應一個測試，名稱格式為 `<單號> TC-<編號> <Test Case 標題>`，例如 `ZHC-1 TC-3 未登入上傳 jpg 成功`
- 不合併多條 Test Case 到一個測試，也不把一條拆成多個
- 不撰寫任何沒有對應 Test Case 的測試

**預期結果**

- 斷言必須等同 Test Case 的 Then。Test Case 寫「顯示 900 元」，就檢查文字是 900 元，不可以只檢查「有顯示金額」，也不可以多檢查 Test Case 沒提到的東西
- Given 的前提由測試自己建立（透過畫面操作或系統提供的介面），測試之間不可互相依賴執行順序
- 不寫死網址、帳號、密碼。一律從環境變數讀取，並記錄在 README

**元素定位**

- **既有的畫面元素**：優先用使用者看得到的特徵定位（角色、標籤文字、按鈕文字），參考原始碼確認實際的文字
- **這張單新增的元素**：在 `selectors.ts` 定義 `data-testid`，名稱取自規格「預期畫面」中的元素名稱，轉成英文小寫加連字號，並加上單號以外的功能前綴避免重複（例如 `album-upload-file-list`）。測試一律透過 `selectors.ts` 取用，不在測試中直接寫字串
- `selectors.ts` 是給實作步驟的約定：實作時必須在對應的元素加上這些 `data-testid`。所以每一個定義都要加上註解，說明它對應預期畫面中的哪一個元素

**無法自動化的 Test Case**

有些 Test Case 無法在自動化測試中建立前提，例如需要等待實際時間經過、需要系統改版前的既有資料、需要外部系統配合。這類情況：

- 先確認真的做不到。能透過畫面或系統介面建立前提的，都要自動化
- 確定做不到的，不要寫出一個永遠通過或被跳過的測試。在 README 的對照表中標示為「人工驗證」並說明原因，由步驟 9 的人操作確認
- 人工驗證的數量超過 Test Case 總數的三分之一時，代表這張單的 Test Case 寫法可能不適合自動化：依 2.9 回報問題，由人決定

**Test Case 本身有問題**

以下情況不要自行決定，依 2.9 回報問題：

- 步驟或預期結果不明確，有兩種以上合理的解讀
- 兩條 Test Case 互相矛盾，或與規則矛盾
- 預期畫面中找不到 Test Case 提到的元素

### 2.7 README 對照表

`<TEST_DIR>/<單號>/README.md` 必須包含：

```
# <單號> 測試對照表

規格來源：<規格檔案路徑>

| Test Case | 類型 | 測試檔 | 說明 |
|---|---|---|---|
| TC-1 | 自動 | upload-page.spec.ts | |
| TC-2 | 自動 | upload-page.spec.ts | |
| TC-9 | 人工驗證 | — | 需要改版前已存在的連結，無法在測試中建立 |

## 執行需求

- 環境變數：<列出需要的環境變數與用途，不寫實際的值>
- 前置條件：<例如需要一個有某權限的後台帳號>

## 新增的 data-testid

| data-testid | 對應的預期畫面元素 |
|---|---|
```

每一條 Test Case 都必須出現在對照表中，一條都不能少。

### 2.8 檢查與 commit

1. **語法檢查**：在 `<TEST_DIR>/` 安裝相依套件並執行 `npx playwright test --list`，確認所有測試都能被載入、名稱正確。此時程式還沒寫，**不要實際執行測試**。環境無法安裝套件時略過這一步，並在報告與 Jira 留言中註明「未做語法檢查」
2. **數量核對**：對照表的列數等於這張單的 Test Case 數量；類型為「自動」的列數等於 `--list` 列出的這張單的測試數量
3. **範圍檢查**：執行 `git status --porcelain`，確認所有變更都在 `<TEST_DIR>/` 底下。有其他路徑的變更就還原；`node_modules` 等安裝產物不可以被 commit（確認 `<TEST_DIR>/.gitignore` 有排除）
4. commit 訊息：`test(<單號>): <一句話摘要>`。修正測試用 `test(<單號>): 依備註修正測試 - <摘要>`
5. push 到 `origin feature/<單號>`

### 2.9 回報問題（轉到 STATUS_PROBLEM）

需要人回答時：

1. 已經寫好、沒有疑問的測試照常 commit 並 push，不要丟棄
2. 重新讀取票的狀態，仍是 STATUS_FROM 才繼續
3. 新增留言：

```
【回報問題】步驟 5（撰寫測試）

無法完成測試撰寫，需要確認以下事項：

1. <Test Case 編號>：<問題>。可能的解讀：(a) ... (b) ...
2. ...

已完成的部分：<已撰寫的測試數量與分支連結>

回覆後請依情況轉換：Test Case 需要修改 → A；Test Case 沒錯、只需說明做法 → T
```

4. 轉換到 STATUS_PROBLEM，清空「處理中」

### 2.10 寫回前再確認

重新讀取票的狀態：

- 仍是 STATUS_FROM → 繼續
- 已被改成其他狀態 → 放棄寫回：不轉換、不留完成的留言，只清空「處理中」，在報告中註明。已 push 的內容保留

### 2.11 寫回 Jira

新增留言：

```
【測試完成】步驟 5（自動化）已完成本單的測試撰寫。

**分支**：<分支連結>（commit <短雜湊>）

**測試**：Test Case 共 <N> 條，自動 <A> 條，人工驗證 <M> 條
- 對照表：<README 連結>
- 測試檔：<檔案清單與連結>

**實作時必須遵守**
- 新增的畫面元素要加上 <selectors.ts 連結> 定義的 data-testid（共 <K> 個）
- 不可修改 specs/ 與 tests/e2e/

**人工驗證的項目**（沒有則寫「無」）
- TC-<編號>：<原因>

**語法檢查**：<已通過 / 未執行與原因>
```

修正測試或規格變更後重來時，另外逐條說明這次改了哪些測試、為什麼。

然後取得可用的轉換清單，選擇目標狀態為 STATUS_TO 的那一個。最後清空「處理中」。

## 3. 失敗處理

1. 在票上留言說明失敗在哪一步、錯誤訊息
2. 清空「處理中」
3. 不要轉換狀態
4. 記入報告的失敗清單

同一張票的留言中已經有 3 次以上連續的失敗紀錄時，不要再處理，在報告中標註「需人工介入」。

## 4. 執行報告

```
## 步驟 5 執行報告 <日期時間>

執行環境：<雲端 / 本機>
查詢到：<N> 張（本次處理 <M> 張，其餘留待下次）

### 成功
- <單號> <標題>：<第一次/修正測試/規格變更>，自動 <a> 條、人工驗證 <m> 條，<分支連結>

### 回報問題（已轉 D）
- <單號>：<問題摘要>

### 放棄寫回
- <單號>：狀態已變為 <狀態>

### 失敗
- <單號>：<失敗步驟> - <原因>

### 需人工介入
- <單號>：<原因>

### 未處理的專案
- <KEY>：repo <名稱> 未掛載
```

沒有內容的段落寫「無」。

## 5. 絕對不做的事

這些規則存在的原因是：測試是驗收的標準，必須獨立於實作，而且只能忠實反映人確認過的 Test Case。

- 不修改 `tests/e2e/` 以外的任何檔案。`specs/` 是步驟 3 的範圍，原始碼是步驟 6 的範圍
- 不修改其他單的測試資料夾。共用工具需要調整時，只能新增，不可改變既有行為
- 不改變、放寬或加嚴 Test Case 的預期結果
- 不撰寫沒有對應 Test Case 的測試
- 不用 skip、fixme 或永遠通過的寫法來處理寫不出來的測試
- 不實際執行測試來「確認會通過」，此時程式還不存在
- 不 push 到 `main` 或基準分支、不建立新分支、不開 PR、不 merge、不刪除分支、不 force push
- 不執行 STATUS_FROM → STATUS_TO 與 STATUS_FROM → STATUS_PROBLEM 以外的任何 Jira 轉換
- 不修改票的描述、優先度、負責人等欄位，不修改 subtask
- 不在測試或文件中寫入實際的帳號、密碼、金鑰或內部網址
- 不修改 Request-Hub 的任何內容

## 附錄：第一次建立測試環境

專案的 `<TEST_DIR>/` 還沒有任何測試設定時，建立一個**自成一體**的測試專案，所有檔案都在 `<TEST_DIR>/` 底下，不動專案根目錄的任何設定：

```
tests/e2e/
├── package.json           只包含 @playwright/test 與必要的型別套件
├── playwright.config.ts   baseURL 讀取環境變數 E2E_BASE_URL；失敗時保留截圖與追蹤紀錄
├── tsconfig.json
├── .gitignore             排除 node_modules、test-results、playwright-report
├── README.md              如何安裝與執行、需要哪些環境變數
└── shared/                跨單共用的工具，例如登入
```

- 使用 TypeScript
- 設定測試結束時為每個測試保留截圖，供步驟 8 附到 Jira
- 登入等會被多張單重複使用的操作，寫成 `shared/` 的共用函式；帳號密碼從環境變數讀取
- 專案如果已經在其他位置使用別的測試框架，不要改動它，仍然在 `<TEST_DIR>/` 建立獨立的設定，並在 Jira 留言中註明
- 在這張單的 Jira 留言中額外說明「本次為這個專案第一次建立測試環境」，提醒人在步驟 9 審查時一併確認設定
