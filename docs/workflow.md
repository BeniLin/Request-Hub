# 自動化需求開發流程

本文件是整個流程的完整說明，供團隊成員與 Claude 參考。

## 狀態定義

| 狀態 | 名稱 | 處理者 |
|---|---|---|
| A | 待寫規格 | AI |
| B | 待確認規格 | 人工 |
| C | 待實作 | AI |
| D | 待人工處理 | 人工 |
| E | 待驗證 | AI |
| F | 待審查 | 人工 |
| G | 待寫 ChangeLog | AI |
| H | 待上版核准 | 人工 |
| I | 待發版 | AI |
| J | 已發版 | — |

Jira 自訂欄位：

- **處理中**：AI 撈到單子時勾選（鎖單），處理完取消
- **退回次數**：每次被退回 C 時 +1

## 流程

1. 由人工與 AI 描述需求，透過不斷的問答把需求完備（本工作區）

2. AI 將結論寫進 Jira 主單並建立 subtask，狀態為 A（本工作區）

3. AI 撈取所有 A 的單子，從最新的 main 建立分支（一張主單一個分支，命名為 `feature/<單號>`），參考目前的文件，在分支內新增或更新需求文件，並撰寫 Test Case 與預期畫面放在分支中，commit 後將文件與 Test Case 連結寫進 Jira，狀態壓 B（若是被退回的單子，在原分支上修改，不重建）

4. 人工撈取所有 B 的單子，確認需求文件與 Test Case 是否正確。OK 則狀態壓 C；不 OK 則將意見寫進 Jira 備註，狀態壓回 A（本工作區）

5. AI 依優先度撈取所有 C 的單子，同步最新 main 後進行實作：
   - 實作細節的文件修改（`docs/`），直接在分支內修改並記錄在 Jira
   - 需求變更或需要修改 Test Case（`specs/`），將問題寫進 Jira，狀態壓 D
   - push 後由 Jenkins 執行單元測試，失敗則自行修正，修不好則寫進 Jira 壓 D
   - CI 通過則開立 PR，將結果與修改過的檔案寫進 Jira，狀態壓 E

6. 人工撈取所有 D 的單子，回覆問題或補充需求。實作層面的問題回覆後壓回 C；涉及需求或 Test Case 變更則壓回 A（本工作區）

7. AI 撈取所有 E 的單子，將分支部署到預覽環境，依照 Test Case 進行驗證並截圖，結果寫進 Jira 與 PR。全部 Pass 則狀態壓 F；有 Fail 則將原因寫進 Jira，退回次數 +1，狀態壓回 C

8. 人工撈取所有 F 的單子，對照預期畫面確認截圖，並 Code Review PR。OK 則狀態壓 G；不 OK 則將修改意見寫進 Jira 備註，退回次數 +1，狀態壓回 C（本工作區）

9. AI 撈取所有 G 的單子，在分支中新增 ChangeLog 片段檔（`changes/<單號>.md`），狀態壓 H

10. 人工撈取所有 H 的單子，做最終上版核准。OK 則狀態壓 I；不 OK 則寫備註壓回 C（本工作區）

11. (Manual, Scheduled) AI 依優先度逐張處理所有 I 的單子：同步最新 main、重跑 CI 與自動驗證、通過才 merge；有衝突或失敗則壓回 C。全部處理完後組合 ChangeLog、決定版號、打 tag 並打包，狀態壓 J

## 共通規則

- **鎖單**：AI 撈到單子後先勾「處理中」，處理完才取消
- **重試上限**：退回次數超過 3 次，AI 不再處理，直接壓 D 交給人
- **Test Case 保護**：只有步驟 3 可以修改 `specs/`，其他步驟需要改一律壓 D
- **權限**：main 開啟 branch protection，必須 CI 通過才能 merge；只有步驟 11 的帳號有 merge 權限

## 文件修改的判斷原則

實作過程中需要改文件時，判斷依據是：**改完之後 Test Case 還成立嗎？**

- 成立：實作細節，AI 直接在分支內修改 `docs/`
- 不成立：需求變更，壓 D 交給人
