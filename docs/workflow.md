# 自動化需求開發流程

本文件是整個流程的完整說明，供團隊成員與 Claude 參考。

## 狀態定義

| 狀態 | 名稱 | 處理者 |
|---|---|---|
| A | 待撰寫規格 | AI |
| B | 待確認規格 | 人工 |
| T | 待寫測試 | AI |
| C | 待實作 | AI |
| D | 待人工處理 | 人工 |
| E | 待驗證 | AI |
| F | 待審查 | 人工 |
| G | 待寫 ChangeLog | AI |
| H | 待上版核准 | 人工 |
| I | 待發版 | AI |
| J | 已發版 | — |

Jira 自訂欄位：

- **處理中**（日期時間）：AI 撈到單子時寫入目前時間（鎖單），處理完清空。超過時限未清空視為卡住，可重新撈取
- **退回次數**（數字）：每次被退回 C 時 +1

## 狀態轉換

| 從 | 到 | 轉換名稱 | 誰 |
|---|---|---|---|
| （建單） | A | 建立單子 | 人 + AI |
| A | B | 撰寫規格 | AI |
| B | T | 核准規格 | 人 |
| B | A | 退回規格 | 人 |
| T | C | 撰寫測試 | AI |
| T | D | 回報問題 | AI |
| C | E | 完成實作 | AI |
| C | D | 回報問題 | AI |
| D | C | 回覆問題 | 人 |
| D | T | 修正測試 | 人 |
| D | A | 變更需求 | 人 |
| E | F | 驗證通過 | AI |
| E | C | 驗證失敗 | AI |
| F | G | 審查通過 | 人 |
| F | C | 審查退回 | 人 |
| F | A | 變更需求 | 人 |
| G | H | 撰寫 ChangeLog | AI |
| H | I | 核准上版 | 人 |
| H | C | 上版退回 | 人 |
| I | J | 合併發版 | AI |
| I | C | 合併失敗 | AI |

退回到 C 的轉換（E、F、H、I → C）都會讓退回次數 +1。

## 流程

1. 由人工與 AI 描述需求，透過不斷的問答把需求完備（本工作區）

2. AI 將結論寫進 Jira 主單並建立 subtask，狀態為 A（本工作區）

3. AI 撈取所有 A 的單子，從最新的基準分支建立分支（一張主單一個分支，命名為 `feature/<單號>`），參考目前的文件，在分支內新增或更新規格文件，並撰寫 Test Case 與預期畫面，更新 `specs/INDEX.md`，commit 後將連結寫進 Jira，狀態壓 B。被退回的單子在原分支上依備註修改，不重建

4. 人工撈取所有 B 的單子，確認規格與 Test Case 是否正確。OK 則狀態壓 T；不 OK 則將意見寫進 Jira 備註，狀態壓回 A（本工作區）

5. AI 撈取所有 T 的單子，把 Test Case 轉成可執行的測試腳本：
   - 在同一個分支的 `tests/e2e/<單號>/` 撰寫 Playwright 腳本
   - 每個測試的名稱帶上 Test Case 編號，與 Test Case 一對一對應
   - 斷言內容必須等同 Test Case 的預期結果，不可自行增減
   - 依預期畫面定義每個元素的 `data-testid`，集中寫在一份選擇器檔案中，作為實作必須遵守的約定
   - 由 Jenkins 檢查腳本語法正確、可以被載入
   - Test Case 無法自動化或描述不夠明確時，將問題寫進 Jira，狀態壓 D
   - 完成後 commit，將腳本清單寫進 Jira，狀態壓 C
   - 規格被退回重寫後再次進到 T 時，依變更的 Test Case 更新腳本，不重寫

6. AI 依優先度撈取所有 C 的單子，同步最新基準分支後進行實作，目標是讓步驟 5 的測試通過：
   - 畫面元素必須使用選擇器檔案定義的 `data-testid`
   - 實作細節的文件修改（`docs/`），直接在分支內修改並記錄在 Jira
   - 不可修改 `specs/` 與 `tests/e2e/`。需要變更需求、Test Case，或認為測試腳本有誤時，將問題寫進 Jira，狀態壓 D
   - push 後由 Jenkins 執行單元測試，失敗則自行修正，修不好則寫進 Jira 壓 D
   - CI 通過則開立 PR，將結果與修改過的檔案寫進 Jira，狀態壓 E

7. 人工撈取所有 D 的單子，回覆問題或補充需求（本工作區）：
   - 實作層面的問題：回覆後壓回 C
   - 測試腳本需要修正，但 Test Case 本身沒錯：壓回 T
   - 需求或 Test Case 需要變更：壓回 A

8. AI 撈取所有 E 的單子，將分支部署到預覽環境，由 Jenkins 執行步驟 5 的測試腳本並截圖，結果寫進 Jira 與 PR。全部 Pass 則狀態壓 F；有 Fail 則將原因寫進 Jira，退回次數 +1，狀態壓回 C

9. 人工撈取所有 F 的單子，對照預期畫面確認截圖、Code Review PR，並確認每條 Test Case 都有對應的測試（本工作區）：
   - OK：狀態壓 G
   - 實作與規格不符：將修改意見寫進 Jira 備註，退回次數 +1，狀態壓回 C
   - 規格本身需要調整（例如看到成品後想改設計）：寫入【需求變更】備註，狀態壓回 A

10. AI 撈取所有 G 的單子，在分支中新增 ChangeLog 片段檔（`changes/<單號>.md`），狀態壓 H

11. 人工撈取所有 H 的單子，做最終上版核准。OK 則狀態壓 I；不 OK 則寫備註，退回次數 +1，狀態壓回 C（本工作區）

12. (Manual, Scheduled) AI 依優先度逐張處理所有 I 的單子：同步最新基準分支、重跑 CI 與測試腳本、通過才 merge；有衝突或失敗則壓回 C。全部處理完後組合 ChangeLog、決定版號、打 tag 並打包，狀態壓 J

## 共通規則

- **鎖單**：AI 撈到單子後先寫入「處理中」，處理完才清空
- **重試上限**：退回次數超過 3 次，AI 不再處理，直接壓 D 交給人
- **規格保護**：`specs/` 只有步驟 3 可以修改
- **測試保護**：`tests/e2e/` 只有步驟 5 可以修改。實作的 AI 不可為了讓測試通過而修改測試
- **強制檢查**：n8n 在步驟 6 結束時檢查 commit，動到 `specs/` 或 `tests/e2e/` 就強制壓 D
- **寫回前確認**：AI 寫回結果前，先確認單子狀態沒有被人改過，被改過就放棄這次結果
- **權限**：主幹分支開啟 branch protection，必須 CI 通過才能 merge；只有步驟 12 的帳號有 merge 權限

## 文件修改的判斷原則

實作過程中需要改文件時，判斷依據是：**改完之後 Test Case 還成立嗎？**

- 成立：實作細節，AI 直接在分支內修改 `docs/`
- 不成立：需求變更，壓 D 交給人

## 測試腳本有問題時的判斷原則

- 操作方式對不上（元素定位、等待時機）但預期結果沒錯：壓回 T 修正腳本
- 預期結果本身有疑問：這是 Test Case 的問題，壓回 A
